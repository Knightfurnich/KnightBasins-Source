## 5. D — ทบทวนตรรกะสคริปต์ซิงก์ (6 หัวข้อ)

อ้างอิง `kb_sync_from_admin.py` (repo ส่วนตัว, 233 บรรทัด) · **"จำลอง" = ผลจากกล่องทดสอบ `--dry-run` บนเครื่องผม** ชื่อ S0–S8 คือสถานการณ์ที่ผมใส่ใน API ปลอม

### D(1) ด่านจำนวน — มีทางที่ข้อมูลถูกต้องแต่ด่านหยุด **ใช่**
- ด่านที่ใช้จริงคือเพดาน `MAX_HIDDEN_PER_RUN = 3` (บรรทัด 22, 175–176) นับรวมทั้งสีแผ่น สีงานผลิต และอ่างในรอบเดียว
- **ด่าน 10% (`MIN_SELLING_RATIO`, บรรทัด 177–180) ไม่มีวันทำงาน:** การซ่อนเป็นทางเดียวที่ลดจำนวนที่ขายได้ ต้องซ่อน ≥7 รายการ (10% ของ 64 = 6.4, ของ 65 = 6.5) แต่เพดาน 3 หยุดก่อนที่ 4 ⇒ ด่านที่สองเป็นโค้ดตายที่ทำให้ดูเหมือนมีสองชั้น
- **กรณีข้อมูลจริงถูกแต่หยุด:** บอสถอนสีออกจากการขาย 4 สีพร้อมกัน (เลิกสายผลิต/ของหมดพร้อมกัน) → จำลอง S2 (ลบ 4 สีแผ่น): `หยุดโดยไม่แก้ไฟล์ — จะติดธง hidden 4 รายการ (เกินเพดาน 3)` exit 1 · **ผลข้างเคียง:** ซิงก์ **ทั้งหมดหยุด** รวมถึงการเปลี่ยนราคา/เพิ่มสีใหม่ที่ไม่เกี่ยวกัน และข้อความแจ้งเตือน (exit 1) จะส่งซ้ำ **ทุก 10 นาที** จนกว่าจะมีคนแก้ (ด่านไม่มีสถานะ ไม่มี "อนุมัติแล้ว")
- **กรณีข้อมูลผิดแต่ด่านไม่หยุด:** API ตัดรายการหายไป ≤3 รายการ → จำลอง S3 (ลบ 3 สีแผ่น): ผ่านด่าน ติดธง hidden `BW010`, `MU010`, `EG501` (ขายอยู่จริง) ⇒ ฟีดซ่อนสี 3 รายการนานถึงรอบถัดไป (≤10 นาที) แล้ว "เปิดขายกลับ" เอง (บรรทัด 90–93) — ไม่ถาวร แต่ลูกค้าที่ถามช่วงนั้นจะได้ "ไม่มี" · จำลอง S7 (ตัด 3 แผ่น + 3 งานผลิต) → หยุดถูกต้อง (6 > 3)

### D(2) ด่านดึงข้อมูล — พลาดได้อีกหลายกรณี
ด่านคือ HTTP 200 + JSON + `sheetStones`/`installedStones`/`basins` เป็น list ไม่ว่าง (`fetch`, บรรทัด 37–46)
1. **`active` ถูกเมินทั้งหมด:** สคริปต์ไม่อ่านฟิลด์ `active` (ค้นไม่พบในไฟล์) ถือว่า "ปรากฏในรายการ = ขาย" จำลอง S6 (ตั้ง `active:false` ที่สีหนึ่ง) → ไม่มีการเปลี่ยนใด ๆ ⇒ ถูกต้องเฉพาะตราบที่ `/api/catalog` กรองเฉพาะ active เอง (ตอนนี้ทุกแถวเป็น `active:true`) ถ้า API เปลี่ยนให้ส่งแถวที่ปิดไว้ด้วย สีที่ปิดจะยังขายใน KB
2. **รายการที่ขาด `code`/`sku`:** `norm(None)` ได้สตริงว่าง หลายแถวชนกันที่คีย์ `""` (บรรทัด 65–67) แถวที่เหลือถูกกลืนเงียบ ๆ
3. **ข้อมูลเก่า (stale):** API ตอบ 200 ถูกต้องแต่มาจาก cache/สำเนาเก่า — ไม่มีการเทียบเวลา/เลขเวอร์ชัน
4. **ไม่มี retry:** ช่วง deploy ที่ api ถูก recreate (สิบกว่าวินาที; รอบ 298 พบ 502 จริง) ถ้ารอบ 10 นาทีตรงช่วงนั้นจะ `abort` + ส่งข้อความผิดพลาดหลอก (ความน่าจะเป็นต่อ deploy ≈ 20 วินาที ÷ 600 ≈ 3% — ลดลงมากหลัง `paths-ignore` ของ #428)
5. **ไม่ตรวจขนาดขั้นต่ำ/จำนวนอ่าง:** `basins` แค่ "ไม่ว่าง" API ที่ตัดเหลือ 1 อ่างผ่านด่านดึงข้อมูล (แต่จะโดนเพดานซ่อน 3 ที่ 4+ อ่านที่หายไป)

### D(3) ราคา 0/ว่าง/ติดลบ = ข้ามพร้อมรายงาน — มีราคาจริงเป็น 0 ได้ **ในธุรกิจนี้ แต่ไม่ใช่กับสี**
- ฟีดเองมีรายการราคา 0 จริง: `addons` → `basin_stopper` "สะดืออ่างรุ่นมาตรฐาน (เมื่อซื้ออ่าง)" ราคา 0 หน่วย "ฟรี" (สคริปต์ไม่แตะ `addons`) ⇒ แนวคิด "ของแถม" มีอยู่ในข้อมูล แต่ยังไม่มีสี/อ่างที่ตั้งราคา 0
- พฤติกรรมเมื่อราคาสีเป็น 0: `price_ok` (บรรทัด 74–79) ส่ง `continue` ที่บรรทัด 82–84 → **ไม่อัปเดตและไม่ซ่อน** (เพราะสีนี้ยังอยู่ใน `sheet` จึงไม่ถูกบรรทัด 99–101 ซ่อน) ⇒ KB ขายต่อด้วย **ราคาเดิม** จำลอง S1 (ราคา BW010 = 0): `warns: ["BW010: ราคาแผ่นผิดปกติ (0) — ข้าม"]` ไม่หยุด
- ความเสี่ยง: ถ้าบอสตั้งราคา 0 เพื่อ "เลิกขาย/ติดต่อสอบถาม" ฟีดยังขายราคาเก่า และเข้ากับปัญหา D(5)-ค้างวน (ดูข้างล่าง)

### D(4) lock ค้าง — ค้างถาวร **ใช่** (ทดสอบแล้ว)
- ไฟล์ lock เขียนที่บรรทัด 57 ลบที่ `finally` (บรรทัด 228–229) **ไม่มีการเช็คอายุ** (ค้นคำว่า mtime/age/ttl ไม่พบ) ถ้าโปรเซสถูกฆ่าแบบที่ `finally` ไม่ทำงาน (`SIGKILL`; และ `SIGTERM` ของ Python บน Linux จบโปรเซสทันทีโดยไม่เรียก `finally` ในค่าปริยาย — พฤติกรรมของ Python ไม่ได้ทดสอบบนเครื่องนั้น) lock จะค้าง
- **ทดสอบ T1/T2:** รันกับ API ที่ตอบช้า 40 วินาที แล้ว hard kill → lock ยังอยู่ → รันซ้ำ 3 รอบด้วย API ปกติ ได้ `⚠️ KB sync หยุดโดยไม่แก้ไฟล์ — มี lock ค้างอยู่` exit 1 ทั้ง 3 รอบ ⇒ **หยุดถาวรและส่งข้อความผิดพลาดทุก 10 นาที (~85 ข้อความ/วัน)** จนมีคนลบ `.kb_sync.lock`
- เพิ่มเติม: `--dry-run` ก็สร้าง/ถือ lock (บรรทัด 56–57) ⇒ คนที่รัน dry-run ตอนเดียวกับ cron ทำให้ cron รอบนั้น abort+แจ้งเตือน (เล็กน้อย)

### D(5) เขียนแบบ atomic แล้ว `build-public.py` ล้มกลางทาง — ได้สภาพ **"ต้นทางใหม่ + ฟีดเก่า" เงียบ ๆ**
ลำดับ: สำรอง 2 ไฟล์ (บรรทัด 201–202) → เขียน tmp + parse ซ้ำ (204–209) → `os.replace(tmp, SRC)` (210; **ต้นทางเปลี่ยนแล้วที่จุดนี้**) → `os.system("… build-public.py >/dev/null 2>&1")` (212) → `subprocess.run(sync-kb.py)` (213–214) → ส่งข้อความ (216–226) → `return 0`
- **ผลคืนของ `os.system` และ `subprocess.run` ไม่ถูกตรวจ** เอาต์พุตถูกทิ้ง ⇒ ถ้า build ล้ม: `pricing.json` ใหม่แล้ว, `pricing.public.json` (ฟีดที่เสิร์ฟ) เก่า, ข้อความยัง **"อัปเดตฟีด + platform_hints แล้ว"** (บรรทัด 225) และ exit 0
- **ไม่หายเอง:** รอบถัดไปเทียบแอปกับ `SRC` (ซึ่งใหม่แล้ว) → ไม่พบความต่าง → `return 0` เงียบ (บรรทัด 191–192) ⇒ ฟีดเก่าค้างจนกว่าจะมีการเปลี่ยนในแอปอีกครั้ง **และ build ครั้งนั้นสำเร็จ**
- ไฟล์สำรองมีแต่ **ไม่มีโค้ดคืนค่า** อัตโนมัติ · ผมตรวจไม่ได้ว่า `build-public.py` เองเขียนฟีดแบบ atomic หรือไม่ (ไม่มีไฟล์)
- ข้อสังเกตเล็ก: การตรวจซ้ำ `len(check["products"]) < selling_after` (บรรทัด 207) เป็นเงื่อนไขที่เป็นจริงไม่ได้เลย (จำนวนรายการทั้งหมด ≥ จำนวนที่ขาย จากลิสต์เดียวกัน) ⇒ เหลือแค่ "parse ได้ + มี tiers" · `tempfile.mkstemp` สร้างไฟล์สิทธิ์ 0600 แล้ว `os.replace` ทับ `pricing.json` ⇒ สิทธิ์ของไฟล์ต้นทางอาจเปลี่ยน (ผมยืนยันไม่ได้ว่ามีผู้อ่านอื่นหรือไม่) และ fd ที่ `mkstemp` เปิดไม่ถูกปิด

### D(6) allow-list เรต `{7500, 8500, 9500, 12000}` — **ควรมี แต่ต้องมีทางออก** (ตอนนี้ปิดตาย + แจ้งซ้ำ)
- ถ้าแอปเพิ่มสีใหม่ที่เรต 13,500 → จำลอง S5: `warns: ["NEW999: เรตใหม่ 13500 ไม่อยู่ใน allow-list — ไม่สร้างเรตอัตโนมัติ"]` (บรรทัด 114–117) ⇒ **สีนี้ไม่ถูกเพิ่มใน KB** ภายใต้กฎบอส "สีที่ไม่มีใน KB ก็ไม่มีจำหน่าย" บอทจะบอกลูกค้าว่าไม่มีขาย ทั้งที่แอปขาย
- ถ้าสีเดิมเปลี่ยนเรตเป็น 13,500 → จำลอง S4: `warns: ["BW010: เรตเปลี่ยนเป็น 13500 ไม่อยู่ใน allow-list — ไม่ย้าย"]` (บรรทัด 128–130) ⇒ **KB ยังใช้เรตเดิม ผิดจากแอป** ลูกค้าถูกเสนอราคาเก่า
- ทั้งสองกรณีเป็น "คำเตือนค้าง" → ดูผลข้างเคียงข้อ D(7)
- **คำตอบ:** allow-list กันค่าผิด (เช่น พิมพ์ 85000) เป็นพฤติกรรมที่ควรมี แต่ควรมี **ขั้นอนุมัติ**: เตือนครั้งเดียว + ให้บอสยืนยันเรตใหม่ (เช่นไฟล์รายการเรตที่อนุมัติ) แล้วจึงรับเข้า แทนที่จะปล่อยให้ KB ผิดจากแอปแบบเงียบ ๆ

### D(7) ข้อที่ใบไม่ได้ถามแต่สำคัญ: "คำเตือนค้าง" ทำให้เขียนไฟล์ซ้ำทุกรอบ
เงื่อนไข "ไม่มีอะไรเปลี่ยน → เงียบ" (บรรทัด 191–192) รวม `warns` ไว้ด้วย ⇒ ถ้ามีคำเตือนค้าง (S1/S4/S5) ทุกรอบจะผ่านไปถึงส่วนเขียน (จำลอง: โหมด dry ถึงบรรทัด 194 ทุกรอบ) ในโหมดจริงหมายถึงทุก 10 นาที: สำรอง 2 ไฟล์ใหม่ (`.bak-kbsync-<เวลา>` ไม่มีที่ลบ) · เขียน `pricing.json` ใหม่ · สั่ง build + sync-kb · ส่งข้อความเต็ม ⇒ **~85 ครั้ง/วัน · ไฟล์สำรอง ~170 ไฟล์/วัน** โดยไม่มีอะไรเปลี่ยนจริง และ `synced_at` เปลี่ยนทุกรอบ

### D(8) อื่น ๆ
