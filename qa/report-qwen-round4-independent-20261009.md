## C. พิสูจน์ "เงียบเมื่อไม่เปลี่ยน" — **ผลวัดสอดคล้องกับกลไกเงียบ แต่ *พิสูจน์ไม่ได้* ว่า cron ทำงาน (สำคัญ)**

```
$ curl -s https://api.knightbasins.com/kb/pricing.json | python3 -c "...print(json.load(sys.stdin)['synced_at'])"
  sample 1 @20:59:46 TH → synced_at = "2026-10-09 20:11"   (ไฟล์ 58,494 B)
  sample 2 @21:13:04 TH → synced_at = "2026-10-09 20:11"   (58,494 B)   ← ห่าง 13 นาที 18 วินาที ≥ 11 ✅
  sample 3 @21:13:49 TH → synced_at = "2026-10-09 20:11"   (58,494 B)
$ curl -sI ... | grep -i last-modified → Fri, 09 Oct 2026 13:11:32 GMT (= 20:11:32 TH) — ตรงกับ synced_at
```
**จำนวนรอบที่ควรรันในช่วงที่ผมเฝ้า (นับจาก cron `*/10 1-14 * * *` = UTC 01:00–14:59 → 08:00–21:59 ไทย — ผมหาว่า cron แปลง with time-zone ของ boss ถูกต้อง):**
```
การเขียนไฟล์ล่าสุด 20:11:32 → จากนั้นถึง sample 3 (21:13:49) มี tick ที่ควรเกิด:
  20:20 · 20:30 · 20:40 · 20:50 · 21:00 · 21:10  = **6 รอบ** · และไฟล์ไม่เปลี่ยนเลย (0 B ต่าง, same etag family)
```
**สรุปอย่างตรงไปตรงมา (ข้อ C.3 ที่ใบงานบังคับให้ตอบ):**
- ✅ สิ่งที่ทำให้ "ความเงียบเมื่อไม่เปลี่ยนนั้น **ไม่พังไฟล์**" เป็นจริงในช่วงที่วัด: 6 รอบโดยไม่มีการเขียนซ้ำ (ไม่มี churn inode ไม่มีการสลับ schema)
- ⛔ **แต่ยังพิสูจน์ไม่ได้ว่า "เพราะ cron ทำงาน + พบว่าไม่มีอะไรเปลี่ยน"** — สมมติฐานคู่แข่งที่ผลมันเหมือนกันคือ *cron ไม่ได้ติดตั้ง/ไม่ทำงาน/ล้มก่อนเขียน* → จากภายนอกผมเห็นแค่ "ไฟล์ไม่เปลี่ยน" ซึ่งไม่แยกสองกรณีนี้
- ⚠️ จุดอ่อนเชิงหลักฐาน: `last-modified 20:11:32` **ใกล้เคียง tick 20:10 (UTC 13:10) + ~ครึ่งนาที** ⇒ *สอดคล้อง* กับการรันโดย cron แต่ เดวิดก็พึ่งแก้ไฟล์ช่วง 20:1x เช่นกัน (`git log`: #434 20:23, #435 20:37) ⇒ แยก manual/cron ไม่ได้
- **ข้อเสนอ (แก้ให้ตรวจได้จากภายนอก):** เพิ่มไฟล์ **heartbeat เล็ก ๆ ไม่มีข้อมูลธุรกิจ** ที่เขียนทุก tick เช่น `GET https://api.knightbasins.com/kb/sync-heartbeat.json` → `{"tick_at":"...","result":"no_change","guards_passed":6,"rows":{"sheet":64,"install":65,"basin":30,"hidden":7}}` —จะทำให้ C เป็น "พิสูจน์ได้" จริงโดยไม่ต้องเปิด log ในเครื่องให้ใคร (และควรแก้ `synced_at` เป็น **ISO8601 + offset เช่น `2026-10-09T20:11:32+07:00`** เพราะ minute-only ไม่มี timezone ทำให้ reconcile กับ log ยาก + ถ้า host ไม่ใช้ TZ ไทยจะกำกวม)

**จุดที่ "ยังพังเงียบได้" ซึ่งผมยังไม่เห็นใน logic ที่แนบ (เพิ่ม 5 ข้อ):**
1. **การเทียบ "ไม่มีอะไรเปลี่ยน" เทียบกับอะไร?** ถ้า script เรนเดอร์ใหม่ ฟีดทุกครั้งที่รัน (template ต่างกันนิดเดียว = ไฟล์ต่าง) → จะ "รายงานทุก 10 นาที" = spam; reverse ก็จริง: ต้อง normalize (sort, ignore `synced_at`) ก่อน diff · logic ที่แนบไม่ได้ระบุ ⇒ ask เดวิด: diff ที่ระดับ payload canonical หรือระดับ byte?
2. **`source_counts`/`schema_version` ไม่อยู่ในไฟล์** (ผม ตรวจ: keys ของ feed = `image_disclaimer, image_base, effective, currency, vat_percent, vat_note, synced_at, sheet_size, sale_types, sheet_colours, discount_tiers, discount_excluded_codes, basin_models, fabrication, hidden_colours, installation, addons` = 17 keys ⇒ ไม่มี field ที่ทำให้รู้ว่า "ฟีดนี้ regen มาจากแอปก้อนไหน") — คนนอก debug ไม่ได้เวลาไม่ตรงกัน
3. **ไม่มี guard ว่า "ฟีดต้องไม่ reference hidden code ใน context ราคา"** — ตอนนี้ถูกด้วย *โครงสร้าง* ของ `sync` ครั้งนี้ (`hidden_colours`) แต่ logic ที่แนบไม่ได้เขียน invariant นี้ ถ้ามีคนแก้อีกสาย (เช่นย้ายกลับเข้า tiers) ไม่มี test กัน ⇒ ขอ test ที่ assert ว่า `set(hidden_colours) ∩ set(all tier codes) = ∅` และ `hidden rows ไม่มี key(price|rate)` — ปล่อยรันจาก CI (repo สาธารณะทำได้)
4. **ไม่ cover `addons` / `discount_tiers` / `installation.rules`** — logic พูดถึง สีแผ่น/งานผลิต/อ่าง เท่านั้น แต่เอกสาร E ใช้ `installation.rules` ในการคำนวณ (5,000/8,000) และ `discount_tiers` ตัดราคา ⇒ ถ้าฝ่ายขายแก้ค่าดำเนินการใน **แอป** ฟีดจะไม่อัปเดตตาม (ไม่มีใน scope การซิงก์) = **ช่อง "ครึ่ง ๆ ของ source of truth"** ที่บอทคำนวณใบเสนอราคาจากค่าเก่าได้ (นี่คือความเสี่ยงด้านเงิน) ⇒ ควร เพิ่ม guard ให้เทียบสองก้อนนี้ด้วย (หรือประกาศชัดว่า "ค่าดำเนินการ = คงที่ตาม KB, ไม่ sync")
5. **TZ/ความถี่ข้ามเที่ยงคืน:** cron business-hours = `*/10 1-14 * * *` (UTC) ครอบคลุม 08:00–21:59 ไทยแล้ว ✅ (ผม แปลง เอง) แต่ตัว `0 19 * * *` (02:00 ไทย) ซ้อนกับหน้าต่างคืน ⇒ ถ้า 02:00 รันแล้ว *ไม่มี change* มันจบเงียบ (fine) แต่ **ถ้า 02:00 ล้ม จะเงียบจนถึง 08:00 (+6 ชม.)** — logic ไม่มี alert กรณี "job fail" (ต่างจาก "no change") ⇒ ควรแยก: fail → alert เสมอ (ไม่งั้น "เงียบ" = ทั้งสุขภาพและโรค)
