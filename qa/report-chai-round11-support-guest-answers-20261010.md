## สรุป 5 บรรทัด
1. **เปลี่ยนอะไร:** (ก) ข้อความ "อยากได้…" ของ guest ไม่ตกเส้นทางโปรไฟล์อีก — ตอบจากแคตตาล็อก (ช่วงราคา+ตัวอย่างรุ่น) + VAT + ค่าดำเนินการ + 2 ทางต่อ (ข) คำตอบรหัสสินค้าต่อท้าย VAT/ค่าดำเนินการ/คำเตือนสีแล้ว (ค) ตอบ "คุณคือใคร / เป็นคนหรือบอท / อายุ-ลูก" เองว่า "น้องไนท์เป็นผู้ช่วยอัตโนมัติ ไม่ใช่คนจริง" (ง) ตอบ "มีสาขา…ไหม" ว่าไม่มีข้อมูลสาขา + กฎต่างจังหวัดจากราคาจริง (จ) เบอร์ขาย 3 เบอร์อยู่ไฟล์เดียว (ฉ) ไม่เรียกโมเดลสำหรับ guest
2. **เทสต์:** ใหม่ 27 ตัว ผ่านทั้งหมด · `support*` 119 / ผ่าน 113 / ตก 6 (ทั้ง 6 คือกลุ่ม `speakingRate` เดิม) · api เต็มชุด **1264 / 1255 / 9** (รอบก่อนบน main 1237/1228/9 → +27 ตัวของผม · ชุดที่ตกเหมือนเดิม ไม่มีตัวใหม่) · พิสูจน์สองทาง 7 แบบ
3. **ตรวจไม่ได้:** `curl` ใส่ production ตามที่ใบขอ — โค้ดยังไม่ deploy จึงให้ผลของเดิม ผมจึงยิง **เส้นทางจริงของเซิร์ฟเวอร์ในเครื่อง** กับแคตตาล็อกสด (GET `/api/catalog` เมื่อกี้) แทน · `tsc` = 0 (มี 2 error เดิม `speakingRate` เหมือน main) · เส้นทางที่ต้องมี Postgres จริง (ผู้ล็อกอิน) ไม่ได้ลองใหม่ (ไม่ได้แก้)
4. **ความเสี่ยง:** ดูข้อ 7 — หลัก ๆ: ตัวจับ "ต้องการซื้อ" เป็นกฎคำสำคัญ (อาจพลาด/เกินในบางประโยค) · คำตอบสินค้ายาว 335–380 ตัวอักษร (เกินเป้า 250 เพราะต้องมีเงื่อนไขครบ) · ผมเปลี่ยน "ให้ทีมโทรกลับ" เป็น "โทรหาทีม" (ดูข้อ 5)
5. **ข้อเสนอ:** (1) บอยแก้เบอร์โทรฝั่งเว็บ (ยังมีหลายรูปแบบ — ข้อ 4) (2) ถ้าอยากให้ guest "ฝากเบอร์ให้ทีมโทรกลับ" ต้องทำ endpoint รับเบอร์ (ใบใหม่) (3) ย้ายประโยค `image_disclaimer` เข้าค่าคงที่ของแอปให้มีต้นทางเดียว

## 5. ที่เบี่ยงจากใบ / เพิ่มเอง (ต้องรู้)
1. **ไม่ใช้ "ให้ทีมโทรกลับ"** — แชทของ guest ไม่มีช่องรับเบอร์ให้ทีม (เส้นทางรับเบอร์จะบังคับล็อกอิน) ถ้าเขียนว่า "ให้ทีมโทรกลับ" จะเป็นทางตันใหม่และเป็นคำสัญญาที่ระบบทำไม่ได้ ผมจึงเสนอทางที่ทำได้จริง: **เข้าสู่ระบบด้วย LINE** หรือ **โทรหาทีม**. ถ้าบอสต้องการจริง ต้องเพิ่ม endpoint รับเบอร์/สร้างลีด (ใบแยก)
2. **เปลี่ยนน้ำเสียงคำตอบสำเร็จรูปทั้งหมด** ใน `support-intents.ts` จาก "ผม … ครับ" เป็น "น้องไนท์ … ค่ะ" — ก่อนหน้านี้แชทเดียวกันพูดสองเสียง (คำถามธรรมดา = ผู้ชาย, คำถามอื่น = น้องไนท์) · เป็นการแก้ถ้อยคำล้วน ๆ ไม่เปลี่ยนเงื่อนไขของแต่ละ intent
3. **เปลี่ยนพฤติกรรมของผู้ล็อกอินเล็กน้อย 2 จุด:** (ก) "คุณคือใคร/เป็นคนหรือบอท" ได้คำตอบสำเร็จรูปเดียวกัน (เดิมได้ข้อความ ผม…ครับ) (ข) ประโยคซื้อที่พูดถึงสถานที่ ("…สำหรับคอนโด") ไม่เด้งถามยืนยันโปรไฟล์อีก — ทั้งสองจุดตรงกับเจตนาใบ ("ห้ามตกโปรไฟล์") แต่เกินคำว่า guest
4. **ประโยค `image_disclaimer` มีสำเนาในโค้ด 1 ที่** (`IMAGE_DISCLAIMER`) เพราะต้นทางจริงอยู่ในฟีด KB ที่สร้างนอกรีโป (`build-public.py`) และแอปไม่มีค่าคงที่นี้ — ข้อความไม่มีตัวเลข และมีเทสต์ตรึงถ้อยคำให้ตรงกับฟีดที่ผมอ่าน (`GET /kb/pricing.json`) · ข้อเสนอ: ย้ายเข้า `commercialConstants()` ให้ฟีดอ่านจากแอป
5. **เงื่อนไข "ฟรีเมื่อสั่ง 3 ชุดขึ้นไป"** ผมไม่ใส่ เพราะค่านี้ไม่อยู่ในค่าคงที่ของแอป (มีแค่ราคา 5,000) — คำตอบข้อ "ติดตั้งฟรีไหม" จึงบอกค่าดำเนินการจริงแล้วให้ทีมยืนยันเงื่อนไขพิเศษ ไม่กุข้อมูล
6. **"ขอดูรูป" ยังไม่ได้รูป** — ยังเป็นการชี้ไปที่รายการสีหิน (เพิ่มคำเตือนสีแล้ว) การแนบรูป/`cards` ต้องเปลี่ยนสัญญา API และ UI จึงไม่ทำ (ตามใบ ให้ STOP ถ้าต้องเปลี่ยนสัญญา)

## 7. ความเสี่ยง
1. **ตัวจับ "กำลังซื้อ" เป็นกฎคำสำคัญ** (คำแสดงความต้องการ/ถามราคา + คำสินค้าหรือรหัสรุ่น) — ประโยคที่ไม่มีคำเหล่านั้นจะตกไปข้อความ guest เดิม และประโยคอย่าง "ราคา…หินที่บ้านเก่า" อาจถูกจับเกิน · คุมด้วยเทสต์ตัวอย่างบวก/ลบ 10 ประโยค; ควรดูข้อความจริงจากแชทเว็บ 1–2 สัปดาห์เพื่อปรับ
2. **ความยาว:** คำตอบสินค้า/ซื้อ 335–380 ตัวอักษร / 4–6 บรรทัด เกินเป้าสไตล์ (~250 / 2–4 บรรทัด) เพราะใบกำหนดให้ VAT + ค่าดำเนินการ + คำเตือนครบ · ถ้าบอสอยากสั้นกว่านี้ ตัดบรรทัดคำเตือนสีออกจากคำตอบ "ซื้อ" ได้ (ตอนนี้มีเฉพาะคำตอบรหัสสินค้า)
3. **ตัวอย่างรุ่น** ("เช่น KF008") คือรุ่นวางเคาน์เตอร์ที่ถูกสุดในแคตตาล็อกตอนนั้น — เปลี่ยนตามราคา ไม่ใช่การแนะนำเฉพาะราย
4. **เทสต์ fixture:** ภาพถ่ายแคตตาล็อกสด (17 KB) ถูกเก็บในรีโป — ค่าช่วงราคาในเทสต์คำนวณจากไฟล์นี้ ไม่ตรึงตัวเลข จึงไม่ล้าสมัยเมื่อราคาแอดมินเปลี่ยน แต่ถ้าโครงสร้างแคตตาล็อกเปลี่ยน fixture ต้องอัปเดต
5. **ไม่ได้ทดสอบกับฐานข้อมูลจริง/Hermes จริง** ในเส้นทางผู้ล็อกอิน (ไม่ได้แก้โค้ดส่วนนั้นนอกจากตัวกัน propertyType)
