## B. ปิดช่อง — เว็บ ↔ LINE บทสนทนาเดียวกัน

### B.1 สิ่งที่แก้ (`artifacts/api-server/src/lib/hermes-support.ts`)
- ส่งหัว `X-Hermes-Session-Key: agent:main:line:dm:<lineUserId>` ควบคู่ `user` ทุกครั้งที่ถาม Hermes (ฟังก์ชันใหม่ `lineConversationSessionKey`) พร้อมคอมเมนต์อธิบายที่มาของรูปแบบ
- `lineUserId` มาจาก `account.userId` ของ session ที่ยืนยันแล้วเหมือนเดิม (`routes/support.ts:432`) — ข้อความของลูกค้าไม่มีทางกำหนดคีย์ (มีเทสต์)
- ใส่หัวเฉพาะ `^U[0-9a-f]{32}$` (รูปแบบรหัสผู้ใช้ LINE) — id ผิดรูปแบบ (เช่น มี `\r\n`) ไม่ถูกใส่ในหัว และพฤติกรรมเดิมคงอยู่
- ไม่แตะไฟล์อื่น (เทสต์เพิ่ม/แก้เฉพาะ `test/hermes-support.test.ts`)

### B.2 รูปแบบคีย์ — ไม่ตรงกับใบ (รายงานแทนการเดา)
ใบเสนอ `line:<lineUserId>` ผม **ไม่ใช้** เพราะหลักฐานในรีโปของเดวิดเองชี้ว่า Hermes เก็บ session ของ LINE DM ไว้ใต้คีย์ **`agent:main:line:dm:<lineUserId>`**: `bin/_test_shared_transcript.py:8` (`KEY = "agent:main:line:dm:U7eb1aaf9…"`, สคริปต์ที่ตั้งชื่อว่า "Decisive test") และบรรทัด 45 ส่งคีย์นั้นในหัว `X-Hermes-Session-Key`; `bin/_inspect_session_keys.py` ดึง `session_key` ของ `source='line'` มาดูรูปแบบ · แพตช์ `KNIGHT_SHARED_SESSION_CHAT` (`fix_shared_session.py`) ค้น session ตาม `session_key` **ตรง ๆ** (`WHERE s.session_key = ?`) จึงต้องเป็นสตริงเดียวกับที่ LINE gateway บันทึก ถ้าส่ง `line:<id>` จะหาไม่เจอแล้วเริ่มบทสนทนาใหม่ว่างเปล่า (ปัญหาเดิมที่ใบต้องการแก้)
เทสต์ mutation M2 (สลับเป็น `line:`) ตก 4 ตัว — พิสูจน์ว่าเทสต์ยึดรูปแบบจริง

### B.3 พิสูจน์ transcript จริง — **ผมทำเองไม่ได้**
ต้องการ (ก) ถามผ่านเว็บหนึ่งครั้งด้วย session ลูกค้า = POST ไป production แชทในฐานะลูกค้า (นอกที่ใบอนุญาต) และ (ข) อ่าน `state.db` ของ Hermes ซึ่งเข้าไม่ถึง · สิ่งที่ผมยืนยันได้คือฝั่งแอป: หัวถูกส่งด้วยค่าที่ถูก (เทสต์ + บันเดิล) · สิ่งที่ **เดวิดต้องยืนยัน** (ใช้สคริปต์เดิม `_test_shared_transcript.py` หรือให้บัญชีทดสอบถามผ่านเว็บ 1 ครั้งหลัง deploy): `session_key = agent:main:line:dm:<userId>` มีแถว `source='api_server'` หรือข้อความใหม่ถูกต่อท้ายใน session LINE เดิม (message_count โต) และข้อความฝั่งเว็บกับฝั่ง LINE อยู่ใน session id เดียวกัน

### B.4 ความเสี่ยง (ข้อ B)
- **context ของเว็บเข้า transcript LINE:** แอปส่ง `contextSummary` (สรุปใบเสนอราคา/ข้อมูลลูกค้า) เป็นข้อความ `system` ทุกคำถาม เมื่อใช้ session ร่วมกัน Hermes อาจบันทึกลง transcript เดียวกับที่บอท LINE ใช้ ⇒ ข้อมูลบัญชีเว็บของลูกค้าคนนั้นเข้าไปอยู่ในบทสนทนา LINE ของเขา (คนเดียวกัน ไม่รั่วข้ามคน) แต่ transcript อาจบวมซ้ำทุกคำถาม — **ตรวจไม่ได้ว่า Hermes เก็บหรือไม่** ให้เดวิดเช็กตอนยิงพิสูจน์
- ตัวตน/สไตล์ของ platform `api_server` กับ `line` ต่างกัน (persona คนละไฟล์) แต่ประวัติร่วมกัน — โมเดลอาจเห็นบทสนทนา LINE (ที่ตอบสไตล์ LINE) แล้วต้องตอบสไตล์เว็บ ไม่น่าเสียหายแต่ควรดูผลจริง
- ถ้า Hermes เปลี่ยนรูปแบบคีย์ (เช่น เปลี่ยนชื่อ agent จาก `main`) การแก้นี้เงียบหาย (กลับไปเป็นบทสนทนาแยก ไม่ error) — ค่าคงที่อยู่ที่ `LINE_DM_SESSION_KEY_PREFIX` จุดเดียว

## C. ประเมินทางตายของ LINE push ในแอป (ไม่แก้โค้ด — บอสตัดสิน)

**สิ่งที่พบในโค้ด:** `lib/sales-notifications.ts:54–56` เลือกช่องทางจาก `NOTIFY_CHANNEL` — ถ้า **ไม่ใช่** `telegram` ค่าเริ่มต้นคือ **`line`** ⇒ `notifyQuote/notifySketch/notifyPaymentSlip` ไป `sendLineText` (`:436`) ซึ่งต้องมี `LINE_MESSAGING_ACCESS_TOKEN`/`LINE_CHANNEL_ACCESS_TOKEN` + `LINE_SALES_DESTINATION_ID` ถ้าไม่มี → คืน "บันทึกแล้ว แต่ยังไม่ได้ส่งแจ้งเตือน LINE" และ **ทีมไม่ได้รับการแจ้งเตือนเลย** · อีกจุด `routes/admin-router.ts:1677` `sendDashboardBriefingToLine` (ปุ่มส่งสรุป dashboard เข้า LINE) มี **เฉพาะ LINE** ไม่มี Telegram ⇒ ถ้า env ว่างจริง ปุ่มนี้ตอบ "ยังไม่ได้ตั้งค่า LINE…" ทุกครั้ง · การ์ดลีด portfolio (`routes/portfolio.ts`) ใช้ Telegram ตรง ๆ จึงไม่ขึ้นกับเรื่องนี้
**สิ่งที่ผมไม่รู้:** ค่า `NOTIFY_CHANNEL` ใน production จริง (ผมอ่าน env ไม่ได้) — ถ้าเป็น `telegram` แล้ว ทางตายนี้กระทบเฉพาะ dashboard briefing; ถ้ายังไม่ได้ตั้ง ใบเสนอราคา/สลิป/แบบร่างทั้งหมดเงียบ (ซึ่งน่าจะถูกสังเกตเห็นแล้ว จึงเชื่อว่าตั้งเป็น `telegram`) ให้เดวิด/บอสยืนยัน

| ทางเลือก | เหตุผล | ความเสี่ยง |
|---|---|---|
| **(1) เลิกใช้และลบ** โค้ด LINE push ในแอป | Telegram คือช่องที่ทำงานจริง · ไม่ต้องมีสำเนา token OA ในระบบที่สอง (เหตุผลเดียวกับที่ทำ `/knight/line/notify`) · ลบโค้ดที่ไม่เคยรัน ลดพื้นผิว | เสีย dashboard briefing ทาง LINE ถ้ายังต้องการ (ต้องย้ายไป Telegram ก่อน) · เทสต์ที่ผูกกับ LINE (`admin-dashboard-stats`, `sales-notification-stone-image`, `quote-token-expiry`) ต้องแก้ · ถ้า `NOTIFY_CHANNEL` ใน prod ยังไม่ใช่ `telegram` การลบจะทำให้เห็นปัญหาทันที |
| **(2) ตั้งค่าให้ทำงาน** (ใส่ token + destination ใน env) | ได้แจ้งเตือน LINE ถึงทีมตามที่โค้ดตั้งใจ | ต้องใส่ **token OA ซ้ำในแอป** (secret sprawl) · push เข้ากลุ่มต้องรู้ group id ที่ OA อยู่ในกลุ่ม · ซ้ำซ้อนกับ Telegram (ทีมได้ 2 ช่อง) · เงื่อนไขของ OA (โควตา push) · ต้องแก้ production env = เป็นหน้าที่เดวิด |
| **(3) คงไว้พร้อมหมายเหตุ** | แก้น้อยสุด ไม่กระทบเทสต์ | ทางตายยังอยู่: default `line` ทำให้ deploy ใหม่ที่ลืมตั้ง `NOTIFY_CHANNEL` เงียบทั้งระบบ · ปุ่ม briefing หลอกว่าใช้ได้ |

**คำแนะนำของผม: (1′)** — เลิกพึ่ง LINE push ในแอป: ให้ `telegram` เป็นค่าเริ่มต้น (หรือถ้าไม่ตั้ง ให้ log เตือนดัง ๆ) ย้าย dashboard briefing ไป Telegram แล้วลบ `sendLineText`/`sendDashboardBriefingToLine` · ทำเป็นใบแยก หลังเดวิดยืนยันค่า `NOTIFY_CHANNEL` จริง · **บอสเป็นผู้ตัดสิน**
