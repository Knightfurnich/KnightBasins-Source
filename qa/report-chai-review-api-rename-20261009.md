## 6. E — ทบทวน config

ไม่ได้เห็นไฟล์เต็ม จึงตอบจากข้อความตัดตอน + พฤติกรรม nginx + ผลภายนอก

| ประเด็น | ความเห็น | เหตุผล/หลักฐาน |
|---|---|---|
| (1) variable + resolver แทนชื่อตรง | **เห็นด้วย** | ถูกตามพฤติกรรม nginx: `proxy_pass http://ชื่อ:พอร์ต` แบบตรง ๆ จะ resolve ตอน start/reload ถ้า DNS ไม่เจอ → `[emerg] host not found in upstream` และ **ไม่ขึ้นทั้งตัว** (ตรงกับ log ที่เดวิดแนบ) · ถ้าใช้ `set $v …; proxy_pass $v;` + `resolver` nginx จะ resolve ตอนมีคำขอ ถ้าไม่เจอตอบ 502 เฉพาะ location นั้น · **หลักฐานว่า `resolver` อยู่ในขอบเขตที่ใช้ได้จริง:** `/kb/admin/` ตอบ 200 จาก backend (ถ้า resolver ไม่ครอบ location นี้ จะ 502 แม้ container รันอยู่) · ผลข้างเคียงที่ดี: `valid=10s` ทำให้ตาม IP ใหม่ของ container ภายใน 10 วินาทีหลัง recreate (เดิมค้าง IP เก่า) |
| (2) `rewrite … break` รักษา path | **เห็นด้วย** (มี 2 ข้อควรรู้) | เมื่อ `proxy_pass` มีตัวแปรและไม่มี URI nginx จะส่ง URI เดิมทั้งหมดไป backend ไม่ตัด prefix ให้ จึงต้อง `rewrite` เอง — `^/kb/admin/(.*)$ → /$1` ให้ผลเท่ากับ `proxy_pass …/;` เดิม · query string ถูกรักษาอัตโนมัติ · **หลักฐาน:** `/kb/admin/` → 200 md5 เท่าของเดิม · `/kb/admin/index.html` → 404 แบบ **JSON 22 B จาก backend** (ไม่ใช่ 404 ข้อความของ nginx) แปลว่า backend ได้ `/index.html` ถูก prefix แล้ว · ข้อควรรู้: (ก) เมื่อ `proxy_pass` มีตัวแปร nginx **ไม่ทำ `proxy_redirect` อัตโนมัติ** — header `Location` ที่ backend ส่งเองจะไม่ถูกเขียนใหม่ (หน้านี้ใช้ path สัมพัทธ์และไม่พบ `Location` ใด ๆ ใน 5 เส้นที่ยิง จึงยังไม่กระทบ) (ข) path ที่มีอักขระเข้ารหัส (เช่น `%2F`, ชื่อไฟล์ไทย) ถูกถอด-เข้ารหัสใหม่ผ่าน rewrite ต่างจากเดิมเล็กน้อย — ความเสี่ยงต่ำ ผมไม่ได้ทดสอบ |
| (3) route อื่นที่อ้างชื่อ container ตรง ๆ | **ตรวจไม่ได้** ในไฟล์จริง · พบ 1 รายการในไฟล์อื่นที่ผมเห็น | เดวิดว่า `location /` ใช้ `$hermes_api` แล้ว — ผมเห็นเฉพาะข้อความตัดตอน ขอให้เดวิดรัน `grep -n "proxy_pass" nginx.conf` แนบผล (ทุกบรรทัดต้องเป็นตัวแปร) · **ใน repo:** `deploy/hostinger/nginx.conf:81` `proxy_pass http://knightbasins-api:8080;` เป็นชื่อตรง ๆ ชนิดเดียวกัน แต่ **บรรเทาแล้ว** ด้วย `depends_on: api: condition: service_healthy` (`docker-compose.yml:50-52`) ⇒ `docker compose up` จะไม่เริ่ม web ถ้า api ไม่ healthy · ยังเสี่ยงถ้ามีคน `docker restart knightbasins-web` เดี่ยว ๆ ตอนที่ api หยุด |

**เงื่อนไขของการเห็นด้วย (3 ข้อ):**
1. แนบผล `grep -n proxy_pass` ของไฟล์จริงทั้งไฟล์ ว่าไม่มีชื่อ container ตรง ๆ เหลือ
2. ทุกครั้งก่อน recreate `knight-api` ให้ทดสอบ config ก่อน เช่น `docker run --rm --network <net> -v <ไฟล์>:/etc/nginx/conf.d/default.conf:ro nginx:alpine nginx -t` เหตุขัดข้องรอบนี้ป้องกันได้ด้วยด่านนี้ (ผมเข้าใจว่า `nginx -t` ก็ล้มด้วย `host not found` เช่นกัน)
3. เพิ่ม healthcheck ให้ `knight-api` และ `knight-images-admin` (ตอนนี้ `status` แสดง `Up` เฉย ๆ ไม่มี `(healthy)` ต่างจาก web/api/db) เพื่อให้สถานะ `Restarting` ไม่ถูกมองข้าม

**ข้อสังเกตเพิ่ม (ไม่ได้เกิดจากการแก้รอบนี้ — โฮสต์เดิมเป็นแบบเดียวกัน):** `GET /kb/admin` (ไม่มี `/` ท้าย) → `301 Location: http://api…/kb/admin/` (ชี้ `http://`) แล้วถูกยกเป็น https อีกทอด รวม 2 hops จบที่ 200 ควรใช้ `absolute_redirect off;` หรือ `return 301 /kb/admin/;` เพื่อไม่ให้มีขั้น http
