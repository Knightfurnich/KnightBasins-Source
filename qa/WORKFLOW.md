# กติกาการทำงานให้เร็วขึ้น (ลดการอ่านซ้ำ·ตรวจซ้ำ·เปลืองโทเคน)

> ฉบับ 1 · 11 ต.ค. 69 · เจ้าของไฟล์: เดวิด · **บอสชี้ปัญหา 11 ต.ค. 69:** "ทีมมากขึ้นแต่กลับเสียเวลาอ่านซ้ำ ตรวจซ้ำ เพราะคำสั่งส่งเป็นชิ้นเล็ก ๆ ⇒ เสียเงิน เสียโทเคน"

## 1 · ต้นเหตุที่ทำให้ช้า (วัดได้)
| ต้นเหตุ | เกิดจริงเมื่อ | ราคาที่จ่าย |
|---|---|---|
| ส่งคำสั่งเป็นชิ้น | งาน 441-B ได้ 4 รอบคำสั่ง | คนทำงานต้องอ่านย้อน + เดวิดต้องเขียนใหม่ |
| เปลี่ยนขอบเขตกลางทาง | แยก `src/data/**` ออกจาก 441-B หลังเริ่มงาน | PR ต้องปิด (#534) + ทำใหม่ = งานซ้ำ |
| งานค้างพร้อมกันหลายใบ | บอยถือ 5 ใบ | สลับบริบท + ตกหล่น + ต้องทวง |
| ตรวจซ้ำแบบเต็มชุดทุก PR | เดวิดรัน api+web เต็มทุกครั้งที่ merge | ครั้งละ ~5–10 นาที CPU/โทเคน |
| รายงานยาวในแชท | เดวิดส่งบล็อกยาวหลายรอบ | บอสต้องอ่านซ้ำ + เปลืองโทเคน |

## 2 · กติกา 8 ข้อ (ทุกคนยึด)
1. **หนึ่งคน = หนึ่งข้อความ = หนึ่งรอบ** · คำสั่งทั้งหมดอยู่ใน `qa/QUEUE.md` (แหล่งจริงเดียว) — ห้ามส่งคำสั่งแยกเป็นชิ้น
2. **ใบงานต้องสมบูรณ์ในตัวเอง** — ระบุ งาน · ขอบเขตไฟล์ · ห้ามแตะ · หลักฐานที่ต้องแนบ · STOP · ถ้าขาดข้อใด ห้ามเริ่มงาน (ให้ถามครั้งเดียวในข้อความเดียว)
3. **ห้ามเปลี่ยนขอบเขตกลางทาง** — ถ้าจำเป็น ต้องออก "ฉบับแก้" ระบุว่าข้อความเดิมข้อใดถูกแทน (ไม่ใช่เพิ่มข้อความใหม่)
4. **WIP limit 2 ใบต่อคน** — ไม่รับใบใหม่จนปิดใบที่มี · งานที่ยังไม่เริ่ม = ยังไม่ต้องแจ้ง
5. **ตรวจตามความจำเป็น** — ต่อ PR: รัน **เฉพาะเทสต์ที่เกี่ยวข้อง** + `tsc` · รัน **ชุดเต็มรอบละ 1 ครั้ง** (หลังรวบ merge ของรอบนั้น)
6. **หลักฐานต้องมาเองจากผู้ทำงาน** (commit + OS + คำสั่ง + ตัวเลข + ภาพ) — เดวิดจะ **วัดซ้ำเฉพาะข้อที่จะเปลี่ยนคำตัดสิน** (ไม่เกิน 3 ข้อ)
7. **รวม merge เป็นรอบ** — เดวิดรวม PR ที่ผ่านแล้ว merge ทีเดียว ลดจำนวน deploy/CI ที่รันซ้ำ
8. **เอกสารใช้ PR เดียวต่อรอบ** — ห้ามเปิด PR เอกสารหลายใบพร้อมกัน (ทุกใบแก้ `KANBAN.md`/`qa/QUEUE.md` ⇒ ชนกันเอง) ให้อัปเดตทับใน PR เดียวจนจบรอบ
9. **รายงานสั้น** — เดวิดรายงานบอส ≤10 บรรทัดต่อรอบ · รายละเอียดทั้งหมดอยู่ในไฟล์ในรีโป (`qa/` · `KANBAN.md` · `qa/QUEUE.md`) ไม่ยัดในแชท

## 3 · บันทึกเพื่อวัดผล (`qa/COMMS-LEDGER.md`)
ทุกครั้งที่ปิดรอบ ให้จด: จำนวนคำสั่งที่ส่ง · จำนวนครั้งที่ต้องแก้คำสั่ง · จำนวน PR ที่ merge · จำนวนเทสต์ชุดเต็มที่รัน · เวลาที่ใช้
⇒ ใช้ดูว่า "เร็วขึ้นจริง" ไม่ใช่รู้สึก · รอบแรก (R1) = **คำสั่ง 6 ครั้ง / แก้คำสั่ง 3 ครั้ง / PR 8 ใบ / ชุดเต็ม 3 ครั้ง** (ตัวเลขนี้คือจุดตั้งต้นที่ต้องลด)

## 4 · สิ่งที่เดวิดจะทำต่างจากนี้ (ทันที)
- เลิกรายงานเป็นชิ้น: ถ้ามีหลายเรื่อง จะรวมเป็นรายงานเดียวต่อรอบ
- ไม่รันชุดเต็มต่อ PR อีก — เฉพาะไฟล์ที่กระทบ + ชุดเต็มรอบละครั้ง
- ไม่ส่งคำสั่งใหม่ให้คนที่ยังทำงานไม่จบ (เว้นแต่ยกเลิกงานนั้น ซึ่งต้องเป็นฉบับแก้)
- เขียนทุกอย่างลง `qa/QUEUE.md` แล้วอัปเดต "ฉบับ" (R1 → R1.1 → R2) แทนการพิมพ์ซ้ำ

## 9 · รอบที่มีคำขออนุมัติ = ส่ง "คำขออนุมัติ" เท่านั้น (บอส 11 ต.ค. 69)
**ห้ามแนบข้อความสั่งทีม (relay block) มากับรอบที่ยังขออนุมัติบอสอยู่** — เพราะบอสอ่านไม่ทัน/อาจ forward ข้อความทีมไปก่อนตอบอนุมัติ ⇒ ทีมเริ่มงานที่ยังไม่ได้รับอนุมัติ = เสียเวลาซ้ำ
**วิธีทำ:** รอบที่ต้องขออนุมัติ → ส่งแค่ (ก) สรุปสั้น (ข) ตัวเลือก + ข้อเสนอแนะ · **รอคำตอบ** ⇒ รอบถัดไปจึงส่งข้อความสั่งทีม (ฉบับเดียวต่อคน)
